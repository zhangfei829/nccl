Conclusion:

- With default `NUM_SMS=16`, `CHUNK=128` is not an optimization.

- For large tokens (`4096/8192`), dispatch is flat and combine is slightly worse.
- Therefore the large-token gain observed in the 9-cell sweep is not "chunk-only";
  it comes from the combined change of increasing `NUM_SMS` and using `CHUNK=128`.

## Focused Validation (single-config D+C)

After the full 9-cell sweep, a focused validation was run with:

```text
tokens = 4096 8192
configs = (16,64), (32,128), (64,128)
repeats = 2
```

Result:

| tokens | dtype | best single config | dispatch avg us | combine avg us | total avg us | default total us | speedup |
|---:|---|---|---:|---:|---:|---:|---:|
| 4096 | bf16 | `(32,128)` | 587.0 | 565.4 | 1152.4 | 1390.2 | 1.21x |
| 8192 | bf16 | `(64,128)` | 1134.7 | 1137.8 | 2272.5 | 2719.9 | 1.20x |

Focused validation supports a simple group-level tuning rule:

```text
tokens < 4096:  (NUM_SMS=16, CHUNK=64)
tokens = 4096:  (NUM_SMS=32, CHUNK=128)
tokens >=8192:  (NUM_SMS=64, CHUNK=128)
```

## Interpretation

1. Dispatch tuning is only meaningful for large tokens.
   - `tokens <= 256`: default `(16,64)` is already effectively optimal; differences are noise-level.
   - `tokens >= 4096`: `(32,128)` gives a stable 18-19% dispatch kernel speedup over default.

2. Combine prefers more blocks than dispatch in the large-token region.
   - Dispatch large-token best: `(32,128)`.
   - Combine large-token best: `(64,128)`.
   - This means a single group-level knob is a compromise. The clean direction is phase-specific tuning.

3. `CHUNK=128` only wins when paired with higher `NUM_SMS`.
   - At default `NUM_SMS=16`, `CHUNK=128` is neutral or harmful.
   - The useful large-token configs are `(32,128)` and `(64,128)`, not `(16,128)`.
   - `CHUNK=256` did not appear in any best result.

4. FULLMESH is paused.
   - It hung at EP16 `t=16`.
   - Current optimization should focus on HT NV72 tuning and low-token HT path ideas, not FULLMESH.
