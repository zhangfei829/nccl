Conclusion:

- With default `NUM_SMS=16`, `CHUNK=128` is not an optimization.

- For large tokens (`4096/8192`), dispatch is flat and combine is slightly worse.
- Therefore the large-token gain observed in the 9-cell sweep is not "chunk-only";
  it comes from the combined change of increasing `NUM_SMS` and using `CHUNK=128`.

parameter sweep.  The validated run still has large non-kernel time:

Interpretation:

- Large-token non-kernel overhead is size-proportional and very large.
- At `8192`, kernel tuning already reduced the kernel path, but non-kernel
  D+C still costs ~1.14 ms.
- The most likely sources are the HT wrapper's D2D copies and format conversion
  kernels around the main dispatch/combine kernels:
  - dispatch: sparse-to-dense prob conversion, output copy from IPC staging to user tensor, dense-to-sparse output conversion
  - combine: input copy from user expert output to IPC staging, optional dense prob conversion
- Therefore the next optimization must be a stream-op breakdown for HT, not
  another CU/CHUNK sweep.

Next measurement:

```text
Add NCCL_EP_HT_PROFILE=1 (similar to NCCL_EP_FULLMESH_PROFILE) and report:
dispatch: token_stage, dense_prob, ht_kernel, output_copy, output_sparse, total_stream
combine : input_copy, dense_prob, ht_kernel, output_sparse, total_stream
```

Decision target:

- If output/input copies dominate, optimize API/buffer ownership to avoid D2D copies.
- If sparse/dense conversion dominates, optimize or fuse format conversion.
- If the HT kernel still dominates after copies are removed, revisit kernel-level tuning.

## Interpretation

1. Dispatch tuning is only meaningful for large tokens.
   - `tokens <= 256`: default `(16,64)` is already effectively optimal; differences are noise-level.
   - `tokens >= 4096`: `(32,128)` gives a stable 18-19% dispatch kernel speedup over default.

2. Combine prefers more blocks than dispatch in the large-token region.
   - Dispatch large-token best: `(32,128)`.
   - Combine large-token best: `(64,128)`.
   - This means a single group-level knob is a compromise. The clean direction is phase-specific tuning.

3. `CHUNK=128` only wins when paired with higher `NUM_SMS`.
   - At default `NUM_SMS=16`, `CHUNK=128` is neutral or harmful.
   - The useful large-token configs are `(32,128)` and `(64,128)`, not `(16,128)`.
   - `CHUNK=256` did not appear in any best result.

4. FULLMESH is paused.
   - It hung at EP16 `t=16`.
   - Current optimization should focus on HT NV72 tuning and low-token HT path ideas, not FULLMESH.
